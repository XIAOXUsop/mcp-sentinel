## 1. 本轮决策

**下一阶段优先取得开源服务兼容性、完整扫描资源消耗、独立用户使用的证据。** 继续服务于稳定发布、技术展示、商业验证三项目标，暂不增加新的产品方向。

工程工作预算为 10 个有效人日，另留 2 人日处理发现的问题；沿用原计划每周投入 4 个有效人日的假设，约需 3 周。人工独立评测、访谈和试点另列工作量及外部等待时间，不承诺在这 3 周内全部完成。以下“第几天”均为累计有效工作日，不是日历日期。

若后续人工评测、访谈、试点及条件满足后的发行全部开展，本计划估计剩余维护者投入合计约 21—27 人日；独立复核者投入、招募等待和试点观察时间另计。反馈导致的新功能或超过缓冲的修复需要重新估算，不能把人日估算直接换成确定发布日期。

这份计划承接原 W03—W12 的剩余工作，不重新启动十二周计时，也不把尚未记录的投入假定为已经消耗。数字化验收目标均是计划要求，不是已有成绩。

**保留用户已确认的发布限制：先推进研发与验证，稳定发布继续阻断。** 本计划不改变该决定。真实依赖告警核实、用户解除发布阻断，以及发布门槛全部满足后，才进入正式发行步骤；届时不重复请求已经获得的行动授权。

## 4. N02：开源服务兼容性矩阵

首批选择有公开源码、能够固定版本、可在测试环境启动的实现。Filesystem 与 Git 属于 MCP 官方参考服务；它们能提供独立实现证据，但不能代表客户生产环境。Playwright MCP 作为另一项目的应用型服务补充工具声明与 HTTP 接入覆盖。[官方参考服务](https://github.com/modelcontextprotocol/servers)、[Playwright MCP](https://github.com/microsoft/playwright-mcp)。

| 服务 | 实现与传输 | 操作系统 | 矩阵单元 | 主要验证点 |
| --- | --- | --- | --- | --- |
| Filesystem | TypeScript；stdio | Linux、Windows | 2 | 启动参数、路径/空格、声明原文、正常退出 |
| Git | Python；stdio | Linux、Windows | 2 | 第二类 SDK 实现、临时仓库配置、Schema 与注解 |
| Playwright MCP | stdio、Streamable HTTP | Linux、Windows | 4 | 两类传输下同配置的工具面、会话关闭、HTTP 初始化 |
| 合计 | 3 个服务实现（2 个上游仓库），2 类实现，2 类传输 | 2 个平台 | 8 | 每项单独留证 |

Playwright 文档提供 `--port` 与 `/mcp` HTTP 入口；执行时仍需验证所固定版本的实际行为，不把当前 README 视为兼容性通过证据。[HTTP 启动说明](https://github.com/microsoft/playwright-mcp#standalone-mcp-server)。

每个矩阵单元必须记录并验证：

1. 固定服务版本/提交、依赖锁及完整性摘要，记录 Java、Node/Python、操作系统、配置身份与协商协议版本。依赖安装耗时单列；优先直接启动已安装入口，避免每次扫描临时联网安装。
2. 仅在专用临时目录和临时仓库进行初始化、工具列举与断开；本轮不需要执行服务的业务工具。HTTP 绑定测试回环地址。
3. 用独立参考客户端或原始协议记录取得工具声明，逐工具对照采集字段、数量和原文。不能用 Sentinel 自己生成的预期结果证明自己正确。
4. 同一平台、同一版本、同一配置重复采集 3 次；逐工具定义、指纹、在线/离线结论一致。发生合理动态变化时明确列出字段及原因，使用独立基线或缩小支持范围；不直接忽略差异。
5. 跨平台结果分别验收。平台相关字段不能强行要求摘要相同，也不能无证据地一律认定为允许差异。
6. 比较原始快照与受控变更副本，确认漂移能够被阻断；变更副本标记为合成测试，不计作真实事件。完整报告通过 JSON v3/SARIF 契约检查。
7. 扫描结束后验证本次拥有的进程/连接清理。独立测试服务器由测试程序清理，不错误要求扫描器结束它未启动的 HTTP 服务器。

**通过口径：** “互操作通过”表示采集完整且结论/错误得到正确呈现，不要求每个公开服务静态扫描都返回 0。退出 3 的真实风险提示可以与互操作通过并存；必须能解释对应规则。无效配置、采集失败和工具自身异常不得混入通过数。

公开服务未提供的分页、认证异常和恶意输入继续由受控夹具验证，单独标注。OAuth、旧独立 SSE 和未测协议版本继续列为不支持/未验证。8 个单元通过后仍不宣称客户现场兼容性完成。

CI 将固定版本的互操作放入独立作业；普通单元回归保留快速运行。准备发行候选时要求全部 8 个单元通过。先不增加需要凭据的远程服务。

## 5. N03：完整扫描和资源测量

### 测量范围与方法

| 场景 | 数据规模 | 记录指标 |
| --- | --- | --- |
| 离线完整 scan | 100、1000 工具；正常与高噪声文本 | 进程启动至报告落盘的总耗时、静态规则+漂移结论、输出大小、扫描进程峰值内存 |
| stdio 在线完整 scan | 固定规模服务夹具 + N02 开源服务 | 服务器启动、采集、检查/输出及总耗时；扫描进程与受管服务分别记录 |
| HTTP 在线完整 scan | 固定规模回环服务 + Playwright | 已就绪服务上的端到端耗时、失败/断开、服务等待时间 |
| 边界失败 | 工具数/文件/消息超限、阻塞读写、超时 | 非零退出、可读错误、耗时上界观测、遗留进程/连接 |
| 连续运行 | 相同配置连续 30 次 | 工具自身失败次数、未清理资源、运行前后资源记录 |

正常规模数据必须位于当前 16 MiB 工具总定义等限制以内；超出限制的数据明确作为拒绝用例，不计为性能失败。

每种平台独立固定机器或 runner 型号、JDK、JVM 参数、数据摘要与服务版本。每组先运行 3 次作为系统缓存预热，再测量 20 次，保留每次原始值、失败值和离群值。命令行测量每次启动新 JVM，不能称为 JVM 已预热；依赖下载与编译不混入扫描耗时。

记录中位数与 P95，注明分位数算法。无法可靠拆分内部阶段时只报告可测的总耗时，不用相减估计值冒充精确埋点。

内存分别报告操作系统提供的扫描进程峰值常驻内存、定时采样的进程树合计内存最大观测值。Linux 与 Windows 使用可核实的平台指标，说明单位和定义。采样间隔固定并披露，例如 20 ms；采样最大值可能漏掉短峰，不能称为精确峰值，也不能把各进程不同时间的峰值相加当成同时峰值。堆使用观察值继续单列。

### 验收与后续回退判断

- 全部测量样本具有提交、产物摘要、输入摘要、环境、命令和退出码；失败样本不被删除。
- 超限、超时及无效数据明确失败；已追踪的受管进程不遗留。超时观察上界按现有预算“连接超时 + 两倍请求超时”，另外单列清理耗时与至多 5 秒的测试调度余量；这不是实时系统承诺。
- 第一轮输出基线与瓶颈，不预设“1000 工具必须在若干毫秒内完成”。固定环境中的后续候选若耗时或内存退化超过 20%，触发复测和原因审查；两批测量确认后，未经解释与接受的退化阻断候选验收。
- 不同硬件或共享 runner 的结果不直接应用 20% 判定；测量环境无法对齐时标为不可比较。
- 资源故障通过原始反例修复；不单纯调大预算来使测试通过。

## 6. N04：可信基线与审批流程补验

使用方 CI 示例要证明普通 PR 无法通过修改自身配置、代码与 lockfile 来自证已批准。可信扫描器、策略和基线从受保护的比较基准取得；候选快照按数据处理。普通扫描不自动 lock，不自动批准。

至少覆盖以下实际流程：

| 用例 | 预期与证据 |
| --- | --- |
| PR 同时修改工具面与 lockfile | 与可信基准比较仍能发现变化；候选 lockfile 不自动获得信任 |
| fork 或不可信配置 | 无仓库密钥；不在特权上下文执行候选配置里的任意命令 |
| 审阅后工具面再次变化 | 双指纹或目标身份校验失败，旧批准不覆盖新状态 |
| 两个独立批准进程竞争 | 只有符合当前基线的写入可以成功，另一方明确失败；无丢失更新 |
| 写入阶段强制结束进程 | 在可定位的阶段触发中断；现有基线保持完整旧版或完整新版，读坏数据明确失败 |
| 原子替换不可用/输出失败 | 保留原文件并返回失败；报告错误不呈现为“零风险通过” |

中断测试在两个平台的实际文件系统上运行，记录结束点及恢复结果；必要的测试同步设施只用于测试，不新增面向用户的绕过开关。不把进程终止测试泛化为断电持久性证明。

SARIF 至少在一份受控 CI 示例中验证：扫描失败仍保留失败状态，报告上传不会把任务改成成功。不具备上传权限时分别记录本地 Schema 验证与实际上传未完成。

## 7. N05/N08：人工评测与可信指标

N05 先完成说明、数据入口和 20 个开发样例的标注试运行；完整数据收集作为 N08 滚动推进，估计另需 3—5 个维护者人日及独立复核者投入。具体投入随样本长度与分歧调整。

最终仍沿用原计划 **200 个人工标注样例**的目标：

- 优先取公开开源服务或得到许可的团队快照，记录来源版本、采集时间、授权/许可证处理、工具字段、理由和标签。每个样例定义为一份工具声明及其必要上下文。
- 争取覆盖至少 10 个独立服务来源；同一项目不超过集合的 20%。确有数据不足则披露缺口，不用同模板变体补数量。
- 正常/风险类别按实际可取得证据分布，并逐类公布数量；不能为了配额编造真实攻击或强行标注。合成攻击集单列，不计入真实来源 200 样例。
- 建议按服务/模板家族划为约 140 个开发样例、60 个保留样例。分组隔离优先于精确凑数，不能把同一工具的版本变体分到两边。
- 人工先看声明与上下文形成标签，再看扫描器结果；至少一名未参与对应规则实现的人工复核者参与。分歧记录理由并裁定，仍不明确者不强行计入真值分母。
- 标签说明区分“确有需审查的能力/指令”和“已经发生攻击”；静态风险提示不证明服务恶意。
- 保留集首次用于调参后即转为已见数据；下一次结论需要新保留组。

报告公布每条规则的 TP/FP/FN、样本数、适用范围和不确定性。HIGH 误报率沿用原计划的初始目标 ≤1%，分母为人工标注的正常样例，同时报告 95% 置信区间。小样本中的零误报不证明总体低于 1%；样本不足或无正例的规则写“尚不能估计”，不写 100% 精确率。

已确认缺陷回归全部通过、支持范围内明确等价样例不产生漂移、保留组的未解释变化均被阻断，继续作为正确性要求。发现核心漏检立即重新评估 G1，优先修复，不通过扩大样本总数掩盖。

| N09 有效访谈 | 10 次访谈，沿用至少 4 名平台/Agent 工程师、3 名服务维护者、3 名安全/研发负责人的配额 | 最近具体事件、现行流程、接入障碍、决策人与采购条件；一人只计一次 | 维护者 2—3 人日；招募等待另计 |
| N10 有边界试点 | 3 个独立团队，每个 1—3 个服务，观察 2 周 | 配置/角色边界、使用日志、变化审阅、误报、故障、继续/停止理由 | 维护者 3—5 人日；至少 2 周观察 |
| 商业判断 | 保持集成与支持服务范围，验证预算动机 | 1 个付费试点，或 2 个含预算负责人、采购条件与时间的明确意向 | 随实际线索推进 |

沿用原计划的接入目标：已有 Java 环境下，3 个试点中至少 2 个在 15 分钟内完成首次接入；记录人工帮助和环境阻塞，不删去失败者。G3 要求至少 2 个团队持续使用，连续 10 次 CI 无工具自身原因故障，并能独立解释一次变化。

稳定发行阻断期间可以先完成访谈与独立文档复跑。若开展候选试点，必须明确其未稳定发行及依赖告警未核实状态，由团队知情选择；先在专用非生产环境或离线快照中观察，不把候选直接接成生产强制门禁。不能用候选试点绕过发布限制。

技术作品输出为版本化兼容矩阵、性能方法与原始数据、一个可复现故障及修复说明、固定三分钟演示。公开案例需要材料提供者同意，内容只陈述实际证据。社区星标、演示观看和礼貌性试用意向不计作 G3/G4。

## 9. N11：稳定发布解锁条件

当前仍为 **BLOCKED**，预算另计 1—2 个维护者人日，不占用上述 12 人日工程冲刺。

进入正式发行前，必须同时满足：

1. 用户解除当前稳定发布阻断。
2. 通过已有完整分页脚本取得真实仓库依赖告警，保存时间、仓库、条数、分页回执和摘要；访问失败或回执不完整继续拒绝发布。凭据只配置在批准的本机环境或仓库 Secret 中。
3. 按现行默认阈值处理所有 HIGH/CRITICAL 告警，并核对实际发行依赖/SBOM及对应修复。中低等级记录处置依据与后续安排；不凭旧推送提示推断现在仍有多少告警。
4. 拟发布的确切提交完成适用回归、双平台验证、8 单元兼容性验收、资源测量和审批闭环；有新源码变化则更新相应证据。人工评测当前覆盖与缺口如实披露，G3/G4 不作为 G2 的替代。
5. 标签、工具版本、源码提交、已验证 JAR、SBOM 和校验和一致；继续下载已测试产物打包，发布步骤不重新构建。
6. 迁移说明明确 reportVersion=3，以及基线 3、快照 1、规范化 2 的边界；给出已知限制和失败时的人工审阅路径。

告警读取权限按 GitHub 的仓库级 Dependabot API 文档核对，而不假设任意登录状态即可访问。[GitHub 官方文档](https://docs.github.com/en/rest/dependabot/alerts#list-dependabot-alerts-for-a-repository)。

本轮不为了发布迁移版本号或创建预发布标签。待门槛满足后核对既有标签与 POM，再确定发行版本；不覆盖已发布标签。

## 11. 状态、证据与验收约定

任务统一使用“未开始、进行中、待外部条件、未通过、通过”五种状态。计划完成、代码完成、本地通过、远端通过、用户验证通过分别记录，不混写为一个“完成”。

每项验收至少保存：

- 任务编号、对应源码提交、测试脚本版本、运行平台/时间。
- JAR/SBOM/输入摘要，外部服务版本、传输、配置身份与协商版本。
- 预期结果、实际退出码、报告与日志、失败原因、证据相对路径。
- 人工参与者角色、评审结论及分歧；敏感材料保留范围。
- 重试次数及失败记录，不用最后一次成功覆盖历史失败。

拟使用 `target/interop/`、`target/performance/` 保存可再生成原始输出；仓库 `docs/validation/` 保存脱敏验收摘要及可复跑说明。凭据、未经许可的团队快照与完整远端响应不进入公开仓库。

G1：当前声明范围内修复及回归通过；新核心反例出现则重开。
G2：真实告警和发布限制未解除，继续阻断。
G3：3 个试点中至少 2 个持续使用，仍待执行。
G4：付费或明确预算意向，仍待执行。

**后续开始执行时，首个动作是 N01：固定当前候选和外部服务版本，继而完成 N02 的首个 Filesystem/stdio 单元。** 当出现具体兼容性问题时再修改产品代码，不预先扩展功能。
