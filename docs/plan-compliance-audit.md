## 新发现与验收影响

### A01 · P1 · 离线注解的未解释变化仍可被 INFO 掩盖

最小变化：

```json
{"readOnlyHint":true,"destructiveHint":true}
```

改为：

```json
{"readOnlyHint":false,"destructiveHint":"unexpected"}
```

使用同一目标的格式 3 基线和格式 1 原文快照执行默认离线 scan，实际退出 **0**，JSON 为 `PASS`。`diff.paths` 明确包含 `/annotations/destructiveHint`，分级结果却只有 `ANNOTATION_READONLY_FLIPPED / INFO`；同时修改工具标题时也仍然退出 0。

后一个 destructiveHint 值不符合布尔类型要求。本反例证明的是**离线入口接受错误类型后，未解释路径仍被忽略**，没有证明合法在线 MCP 服务也能触发相同绕过。正确行为应先拒绝错误类型；若按不透明扩展处理，也必须为未解释路径保留阻断结果。

原因：`ToolDefinition.fromJson` 只检查 annotations 是对象；`SchemaDiff.annotate` 使用 `asBoolean` 默认值，随后从其他字段集合删除两个已知 hint。`Baseline.diffAgainst` 的最终兜底仍只在分级列表为空时触发。独立保存的结构路径没有反向校验每条路径是否确实获得解释。

对应源码：[注解分级](../src/main/java/io/github/xiaoxusop/mcpsentinel/SchemaDiff.java)、[工具读取](../src/main/java/io/github/xiaoxusop/mcpsentinel/ToolDefinition.java)、[最终兜底](../src/main/java/io/github/xiaoxusop/mcpsentinel/Baseline.java)。对应证据：`fixtures/annotation-type-with-info/` 与 `fixtures/annotation-type-with-title/`。

影响：W02 的“每条结构变化均被解释或保守阻断”尚未成立；G1 重新打开。修复必须覆盖原文快照、基线读取，以及 INFO 与错误类型／未知路径同时变化的 CLI 回归。

### A02 · P1 · 非法 dependentRequired 被规范化修复而未诊断

将输入 Schema 中：

```json
{"dependentRequired":{"value":["aux","aux"]}}
```

改为：

```json
{"dependentRequired":{"value":["aux"]}}
```

独立 Draft 2020-12 验证器确认前者非法、后者合法。候选包却允许将前者保存为基线并读回，二者得到相同指纹；默认离线 scan 退出 **0**，没有差异或无效 Schema 诊断。

原因：[canonicalizeDependentRequiredMap](../src/main/java/io/github/xiaoxusop/mcpsentinel/SchemaCanonicalizer.java) 直接排序去重，没有先检查字符串及唯一性。另一个含引用的 required 重复项样例虽在比较时退出 4，但非法定义仍能写入和读回，说明合法性检查与引用文档的保守规范化尚未分离。

此处不把非法输入与合法 Schema 之间的差异描述为“两个合法 Schema 的语义碰撞”。不符合的是原计划明确要求的“无效 Schema 单独诊断，不能通过规范化修复掩盖”。对应证据：`fixtures/dependent-required-duplicate/` 与 `fixtures/reference-required-duplicate/`。

影响：W01 尚未完整验收，并影响可信基线和快照的输入约束。需先明确支持的方言／关键字验证边界，对已支持关键字拒绝非法形态；验证不能因 `$ref` 触发保守遍历而被跳过。

### A03 · P2 · JSON 契约缺少逐工具指纹和具体失败原因

原计划 W06 要求统一表达工具指纹和错误，W07 要求每个目标独立保留失败原因。当前 JSON 只有整个工具面的两个指纹，没有逐工具名称／出现序号／完整指纹清单。

使用不存在的本地命令触发采集失败，实际退出 2，JSON 能正确记录 `FAILED` 和 `CONNECTION_FAILED`，但没有失败阶段、具体错误或原因。详细诊断只在 stderr；批量 JSON 的目标项使用同一模型，也无法独立解释失败原因。

对应源码：[ScanReport.renderJson](../src/main/java/io/github/xiaoxusop/mcpsentinel/ScanReport.java)、[Reports.failed 与 writeReports](../src/main/java/io/github/xiaoxusop/mcpsentinel/cli/Main.java)。对应证据：`fixtures/json-fingerprints/report.json`、`failed-target-report.json` 和 `failed-target-stderr.txt`。

影响：W06、W07 只能登记为部分完成。应增加逐工具证据和结构化错误对象，并在输出前统一脱敏；用成功、单目标失败、部分目标失败、目标不匹配及输出失败场景验收最终契约。

### A04 · P2 · 发布验收文档漏写 SBOM 构建步骤

README 原先只给普通 verify，随后示例直接运行 `verify_artifact.py`。SBOM 插件仅在 `release-evidence` profile 中启用，而验证脚本必须读取 `target/bom.json`；全新目录中普通 verify 不会生成这个文件。

审计已在发行验收示例前补充 `./mvnw -B clean verify -Prelease-evidence`，并说明使用在线构建。该处属于源码和文档交叉确认；本轮没有在第二个全新环境从头复跑，不能据此把 W10 的外部复跑验收记为通过。

## 按原计划恢复执行的顺序

1. **先关闭 A01、A02。** 将本次反例变成永久测试；入口验证与规范化分开；结构差异的每个路径必须有明确解释或阻断项。正式回归必须检查真实 CLI 退出码，包含 INFO 与未知／错误类型组合。
2. **补齐 W06/W07 契约。** 增加逐工具指纹和逐目标具体失败信息；声明版本兼容策略，核对错误输出不会泄漏配置秘密。按纠正后的说明复跑演示和完整产物验收。
3. **完成资源与互操作证据。** 为 stdio／HTTP 设置解析前响应体限制，验证超时取消和清理；记录真实服务、角色、认证及协商版本。不要用解码后大小检查代替解析前限制。
4. **绑定可复验源码提交。** 关闭核心缺陷后提交候选，在该提交上运行远端双平台和完整发布门禁；核对依赖告警查询权限与结果，再由同一测试产物形成发行证据。先满足 G2，再标记稳定发行。
5. **补齐真实评测。** 收集获许可的快照和 200 个人工独立标注样本，保留样本来源、理由及不确定项；新增未见服务或家族。固定环境测峰值内存并约定回退门槛，披露按规则指标及分母。
6. **推进真实使用与商业轨道。** 按原计划进行 10 次有效访谈、3 个两周试点；记录至少 2 个团队持续使用、首次接入耗时与连续 10 次 CI 稳定性，再执行对应 W12 修复。外部联系对象和渠道尚待维护者选择；不把准备文案计为访谈结果。
