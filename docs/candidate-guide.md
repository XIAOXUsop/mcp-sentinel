# v0.6 候选接入、JSON v3 迁移与复跑

此候选的真实依赖告警核验和稳定发行仍阻断。独立体验从专用环境或离线快照开始，团队知情选择试点范围。

## 固定演示

构建完成并安装 validation/interop 的 Python 验证依赖后，运行：

```text
python scripts/run_candidate_demo.py
```

实际 JAR 完成五步：无变化退出 0、合成描述变化退出 4、使用前后完整指纹批准退出 0、再次扫描退出 0、缺基线退出 5。每步在 target/candidate-demo 保存真实命令、文本、JSON 与退出码。

数据为合成离线声明，演示审批和失败状态，不代表真实攻击事件；脚本通过不计作外部独立复跑。

## JSON v3 消费方迁移

先读取 reportVersion，再用对应 Schema 校验。v3 保留逐工具指纹和结构化错误，并要求 checks：

```json
{
  "reportVersion": 3,
  "checks": {
    "staticRisk": "COMPLETE",
    "drift": "COMPLETE"
  }
}
```

上面是字段片段；完整报告见生成的 target/candidate-demo/01-clean.json。05-missing-baseline.json 中两项为 NOT_RUN，并保留已采集指纹。消费方同时读取最终退出码、status、checks 和 errors，不能仅凭采集完成判断安全。

基线 3、快照 1、规范化 2 不变。旧采集曾丢失的注解扩展无法从旧文件恢复，升级后重新采集和审阅。详见 [报告契约](report-format.md)。

## 两名外部复跑者记录

记录参与者角色、系统、已有 Java 环境、候选提交/摘要、开始与首次成功时间、每次人工帮助和失败步骤。要求能解释一次漂移、一次批准和一次失败。从已有 Java 环境起计时，依赖安装耗时单列。

目前参与者及实际结果未登记。维护者安排后执行，未开展的运行不补填时间。

## 访谈与试点登记

沿用 [试点准备](pilot-kit.md) 的 10 次访谈和 3 个两周试点目标。每次访谈登记“待安排/已约定/已完成”，附具体事件、现有流程、接入障碍、预算负责人及采购条件，空记录不计次数。

试点在第 1、7、14 天记录接入耗时、扫描次数、待审变化、误报、工具故障、绕过原因及继续使用决定。先指定 1—3 个服务、角色、基线负责人和证据保存范围。至少两个团队持续使用且连续 10 次 CI 无工具自身故障才支持 G3；付费或明确预算意向支持 G4。

外部联系由维护者安排，只有明确发送指令后才由代理代发具体邀约。
